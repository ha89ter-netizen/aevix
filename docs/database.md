# База данных и вход в аккаунт

**Сделано.** Ниже — что получилось и что осталось; исходный разбор вариантов сохранён, потому
что он объясняет принятые решения.

Состояние: схема применяется командой `pnpm db:push`, вход по ссылке на почту работает
(`src/lib/auth.ts`, маршруты `/api/auth/*`), проекты вошедшего хранятся в базе через
`/api/projects`, проекты не вошедшего — как и раньше, в браузере. Перенос при первом входе
реализован в `ProjectsProvider` в порядке из шага 5.

**Осталось:** на Vercel добавить `AUTH_SECRET` и `RESEND_API_KEY`, применить схему к боевой базе
и проверить вход настоящим письмом. Без `RESEND_API_KEY` письмо отправить нечем, и на проде вход
работать не будет — локально ссылка вместо письма печатается в консоль сервера.

Код к замене был подготовлен заранее: всё общение с хранилищем идёт через один интерфейс
`ProjectStore` в `src/lib/project-repository.ts`, и его методы асинхронные. Подключение базы —
это новая реализация этого интерфейса, а не переписывание страниц.

## Где создавать базу

Проект развёрнут на Vercel, поэтому база нужна та, что работает без постоянного соединения
(serverless-функции живут доли секунды и обычный пул соединений им не подходит).

**Рекомендую Neon.** Это обычный PostgreSQL, но с пулингом, рассчитанным на serverless.

| | Neon | Supabase | Vercel Postgres |
|---|---|---|---|
| Что это | Postgres | Postgres + готовая авторизация | Тот же Neon под маркой Vercel |
| Бесплатно | 0.5 ГБ | 0.5 ГБ | 0.25 ГБ |
| Плюс | самый простой Postgres для Vercel | авторизация уже внутри | ставится в один клик |
| Минус | авторизацию делать отдельно | больше лишнего для нашей задачи | лимит меньше, цена выше |

**Если хотите быстрее всего** — берите Supabase: там сразу и база, и вход по почте, отдельная
библиотека авторизации не нужна.
**Если хотите проще в поддержке** — Neon плюс Auth.js.

Про объём: один проект — это несколько килобайт JSON. В 0.5 ГБ помещаются десятки тысяч
проектов, так что бесплатного тарифа хватит надолго.

## Регион: сначала Vercel, потом база

Интуитивно кажется, что базу надо ставить поближе к пользователям. Это неверно. Пользователь
обращается не к базе, а к функции Vercel — и уже она ходит в базу, часто несколько раз за один
запрос. Поэтому решает расстояние **функция → база**, а не пользователь → база.

Если функции в Вашингтоне (это значение по умолчанию у Vercel), а база во Франкфурте, каждый
запрос дважды пересекает Атлантику. Несколько запросов на страницу — и это уже секунды на
пустом месте.

Правильный порядок:

1. **Задать регион функций Vercel:** Project → Settings → Functions → Function Region → `Frankfurt (fra1)`.
   У Vercel нет региона в Центральной Азии; для Казахстана и СНГ Франкфурт — ближайший разумный.
2. **Создать базу в том же регионе:** Neon → `AWS eu-central-1 (Frankfurt)`.

Проверьте текущую настройку в панели Vercel: в репозитории региона нет, значит используется
значение по умолчанию (`iad1`, Вашингтон) — если только его не меняли руками в интерфейсе.

Закрепить регион можно и в репозитории, чтобы он не зависел от настроек панели:

```json
// vercel.json
{ "regions": ["fra1"] }
```

Про сами страницы можно не волноваться: статика раздаётся с ближайшей к пользователю точки CDN
в любом случае. Регион влияет только на серверные маршруты (`/api/*`).

### А как же OpenAI?

Маршруты `/api/business-analysis`, `/api/website-concept` и `/api/designer-intent` ходят в
OpenAI, чьи серверы в США. Из Вашингтона до них ближе, чем из Франкфурта.

Это не повод переносить функции: обращение к модели одно на запрос и занимает секунды на саму
генерацию, на фоне которых сотня миллисекунд сети незаметна. Запросов же к базе — много, и
каждый мелкий. Поэтому оптимизируем близость к базе, а не к OpenAI.

## Шаг 1. Создать базу (Neon)

1. Зарегистрироваться на neon.tech через GitHub.
2. Create project → выбрать регион **тот же, где выполняются функции Vercel** (см. ниже).
   Для Казахстана это `AWS eu-central-1 (Frankfurt)`.
3. Скопировать строку подключения (Connection string), она выглядит так:
   `postgresql://user:pass@ep-xxx.eu-central-1.aws.neon.tech/neondb?sslmode=require`
4. Положить её в `.env.local` рядом с проектом:

```
DATABASE_URL="строка_подключения"
```

5. Ту же переменную добавить в Vercel: Project → Settings → Environment Variables.

### Разработка идёт в отдельной базе

В проекте Neon две базы: `neondb` — боевая, прописана **только** в Vercel; `aevix_dev` — для
разработки и тестов, прописана **только** в `.env.local`. Отличаются они одним словом в конце
строки подключения.

Разделение появилось не из осторожности, а по факту: пока строка была одна, проверки входа
«локально» завели три аккаунта и три проекта в базе живого сайта. Тесты аккаунтов заводят и
удаляют пользователей на каждом прогоне — делать это там, где лежат данные клиентов, нельзя.

Завести ещё одну базу можно прямо из SQL:

```sql
create database aevix_dev;
```

Схема накатывается тем же `pnpm db:push` — он работает с той базой, что сейчас в `DATABASE_URL`.

`.env.local` уже в `.gitignore` — строка подключения содержит пароль и в репозиторий попадать
не должна.

## Шаг 2. Таблицы

Минимум, который нужен:

```sql
create table users (
  id          text primary key,
  email       text unique not null,
  created_at  timestamptz not null default now()
);

create table projects (
  id          text primary key,
  user_id     text not null references users(id) on delete cascade,
  -- Весь проект одним JSON: структура уже описана типом Project в коде и меняется от этапа
  -- к этапу. Раскладывать её по колонкам сейчас — значит переписывать схему при каждой
  -- правке модели. Разнести на отдельные таблицы можно позже, когда форма устоится.
  data        jsonb not null,
  updated_at  timestamptz not null default now()
);

-- Список проектов всегда запрашивается по пользователю и сортируется по дате изменения.
create index projects_user_updated on projects (user_id, updated_at desc);
```

## Шаг 3. Вход

Проще всего — вход по ссылке на почту (magic link): не нужно хранить и восстанавливать пароли.

- **Supabase**: встроено, отдельная библиотека не нужна.
- **Neon**: поставить `next-auth`, включить провайдер Email, для отправки писем — Resend
  (3000 писем в месяц бесплатно).

**Как сделано в итоге: без `next-auth`.** Библиотека принесла бы собственный набор таблиц
(`accounts`, `sessions`, `verification_token`) поверх схемы выше, а вся нужная механика — это
одноразовый токен и подписанная cookie, то есть две операции на стандартном `node:crypto`. Всё
лежит в `src/lib/auth.ts`; таблица `login_tokens` добавлена к схеме шага 2.

Что важно в этой реализации:

- в базе хранится **хеш** токена, а не сам токен: дамп базы не должен превращаться в набор
  действующих ссылок для входа в чужие аккаунты;
- токен одноразовый, и гасится условием внутри `UPDATE` — два одновременных перехода по одной
  ссылке не могут оба оказаться успешными;
- сессия — подписанный слепок, а не строка в базе: проверка запроса не требует обращения к базе.
  Плата — отозвать одну сессию нельзя, только сменить `AUTH_SECRET` и разлогинить всех;
- ссылка в письме собирается из `APP_URL` или домена Vercel, а не из заголовка `Host`: иначе
  подделанным `Host` можно заставить сервер отправить человеку ссылку на чужой домен.

## Шаг 4. Подключить к приложению

Написать серверную реализацию `ProjectStore` — она должна ходить на свои API-маршруты,
а не в базу напрямую (строка подключения не должна попадать в браузер):

```ts
// src/lib/project-store-server.ts
import type { ProjectStore } from "./project-repository";

export const serverProjectStore: ProjectStore = {
  async load() {
    const response = await fetch("/api/projects");
    if (!response.ok) return [];
    return response.json();
  },
  async save(projects) {
    await fetch("/api/projects", {
      method: "PUT",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(projects),
    });
  },
  async clear() {
    await fetch("/api/projects", { method: "DELETE" });
  },
};
```

И заменить одну строку в `src/lib/project-repository.ts`:

```ts
export const projectRepository: ProjectStore = serverProjectStore;
```

Больше в приложении менять нечего — страницы и компоненты работают через `useProjects()`.

## Шаг 5. Перенести то, что уже есть у людей (не пропускать)

Это важнее самой замены хранилища. Если просто переключиться на сервер, то в день запуска
авторизации у всех, кто уже работал в AEVIX, проекты исчезнут — они останутся в браузере,
но приложение туда больше не смотрит.

Для этого в коде уже есть `readLocalProjectsForMigration()`. Порядок при первом входе:

1. прочитать проекты из браузера;
2. если они есть — отправить на сервер и привязать к аккаунту;
3. только после подтверждения записи очистить локальные;
4. если запись не удалась — **ничего не удалять** и показать ошибку.

Порядок именно такой: сначала убедиться, что данные сохранены на сервере, и только потом
удалять с устройства. Наоборот — значит однажды потерять чужую работу из-за сетевого сбоя.

## Сколько это стоит

- База: 0 ₽ на бесплатном тарифе, дальше от ~$19/мес при заметном росте.
- Письма для входа: 0 ₽ до 3000 писем в месяц.
- Хостинг: как сейчас.

То есть **на старте бесплатно**. Основные затраты — время на реализацию, а не деньги.

## На что обратить внимание

- **Сохранение на каждое изменение.** Сейчас проект пишется при каждой правке — для браузера
  это бесплатно, для сети нет. Понадобится задержка перед отправкой (сохранять через
  секунду после последней правки, а не сразу).
  *Сделано:* задержка в секунду, но только для вошедших — локальная запись осталась мгновенной.
  Задержка создаёт окно, в котором правка живёт лишь в памяти, поэтому на `pagehide` пишется
  досохранение с `keepalive`.
- **Проверка на сервере.** Клиент может прислать что угодно. Валидировать данные в маршруте,
  а не полагаться на то, что их сформировало наше же приложение.
  *Сделано:* маршрут прогоняет присланное через `normalizeProjects` — ту же нормализацию, что
  и браузер (`src/lib/project-schema.ts`), чтобы две проверки не разъехались.
- **Чужие проекты.** В каждом запросе проверять, что проект принадлежит текущему
  пользователю — иначе по подобранному id можно открыть чужой.
  *Сделано:* чтение и удаление фильтруются по `user_id`, а запись защищена условием
  `where projects.user_id = ...` прямо в `on conflict do update`. Если id занят другим
  аккаунтом, запись не происходит, и маршрут отвечает 409, а не молчаливым «сохранено».
